# Аудит багов anvil — проверка по исходникам

Дата проверки: 2026-08-22. База: `main` @ `8ccb1c1` (это тег **v1.0.56** + один docs-коммит).
Незакоммиченные изменения в рабочей копии — perf-рефакторинг (persistent containerd-клиент,
`persistent_client.go`), поведение багов не меняет.

Источники доказательств: код guest-agent и `Sources/vz-runner`; отладочные логи в корне репо
(`guest-agent.log` от 11–14.07 — живая сессия проекта `pprb_uzp_efficiency`, `bk-*.log` от 16.08 —
дебаг buildkit); копия `/var/lib` из VM (`var-lib/`); исходники nerdctl v2.3.5 (версия закреплена
в `Makefile:249`); интеграционный сюит `scripts/integration_tests.py`.

Легенда статусов: **ПОДТВЕРЖДЁН** — воспроизводится в текущем коде; **ЧАСТИЧНО ИСПРАВЛЕН** —
фикс есть, но остались дыры; **ИСПРАВЛЕН** — в HEAD не воспроизводится; **ВНЕ ANVIL** —
первопричина не в коде anvil.

## Текущие баги

### 1. `docker build` сломан целиком — нет buildkitd

**Статус: ЧАСТИЧНО ИСПРАВЛЕН** — сборка реализована и в v1.0.56 присутствует; осталась гонка
первого бута.

**Симптом.** Падают и BuildKit (buildx), и «классический» билдер (`DOCKER_BUILDKIT=0`).

**Диагностика.** В репо: классический билдер — это `POST /build` → `nerdctl build`
(`guest-agent/build.go:60-125`), а `nerdctl build` сам требует buildkitd — комментарий прямо
это говорит (`build.go:96`). Поэтому при отсутствии buildkitd падают **обе** ветки — наблюдение
«сломан целиком» корректно по устройству системы. buildkitd v0.32.2 кладётся в initramfs как
`/opt/buildkit.tar.zst` и распаковывается фоновой задачей stage2 на персистентный диск при
первом буте (`scripts/build_initramfs_containerd.sh:710-719`), лениво стартует
`ensureBuildkitd` (`guest-agent/buildkit.go:39-97`), buildx-remote ходит через vsock:1026
(`buildkit.go:118-155`).

Хронология фиксов: `5d5bab0` (04.08) — классический /build; `566b504` (05.08) — buildx remote;
`6d3a1c0` (15.08) — OAuth-зависание при pull (см. баг №10); `8eeb9c3` (18.08) — бинари сборки
перенесены на диск. Всё это уже внутри тега v1.0.56. Логи `bk-solve.log`/`bk-go-debug.log`
(16.08) показывают успешный build+solve alpine — на починенной версии build работает.

**Остаточная дыра в HEAD:** `ensureBuildkitd` ждёт появления бинаря всего 5 секунд
(`buildkit.go:60-65`). Билд, запущенный сразу после холодного бута, может проиграть фоновой
распаковке тарбола и упасть с «start buildkitd: no such file or directory». Если «свежий anvil»
был старше 04.08 (brew мог отдать прошлый релиз) — buildkitd там не было вовсе.

**Чем опасно.** Невозможность собрать образ локально; обход «кросс-компиляция на хосте +
маунт бинаря в контейнер» расходит окружение разработки с CI/продом.

**Обход, зашитый в проект.** Собственный бинарник кросс-компилируется на macOS-хосте и
бинд-маунтится в контейнер; Dockerfile фактически не используется.

### 2. `docker commit` не реализован — 404 page not found

**Статус: ПОДТВЕРЖДЁН** (в HEAD).

**Симптом.** `docker commit <id>` → `404 page not found` (plain text, не JSON-ошибка Docker).

**Диагностика.** В маршрутизаторе Docker API (`guest-agent/dockerapi.go:447-886`) обработчика
`POST /containers/{id}/commit` нет вообще — запрос проваливается в `http.NotFound`
(`dockerapi.go:885`), который отдаёт именно «404 page not found». grep по guest-agent
находит только `GitCommit` в /version. Заодно: `GET /containers/{id}/export` тоже не
маршрутизирован — `docker export` так же упадёт.

**Чем опасно.** Нельзя зафиксировать состояние контейнера как образ (дебаг «сломанного»
состояния, передача внутри команды).

**Обход, зашитый в проект.** Не использовать commit; всё состояние — в файлах/томах, образы —
только через build (а фактически — внешняя сборка, см. №1).

### 3. Named volumes молча теряются (`-v name:path`)

**Статус: ПОДТВЕРЖДЁН** (в HEAD) — корень найден и доказан.

**Симптом.** `-v name:/path` создаёт контейнер, данные живут в слое контейнера / «не в том
томе»; до пересоздания всё выглядит рабочим.

**Диагностика (по коду и логам).**
1. `POST /volumes/create` у anvil **всегда** создаёт том в namespace `default`
   (`guest-agent/volumes.go:172` — `ns := "default"`).
2. Контейнер compose создаётся в namespace проекта: `ns = labels["com.docker.compose.project"]`
   (`guest-agent/containers.go:563-566`), и `-v name:path` уходит в nerdctl как есть
   (`containers.go:707-728`).
3. Хранилище томов nerdctl — **персоздовое**: `var-lib/nerdctl/1935db59/volumes/<ns>/…`
   (копия из VM в корне репо). В namespace проекта тома нет — и nerdctl v2.3.5 **молча
   автосоздаёт новый** том с тем же именем в namespace проекта, **без labels**
   (`pkg/mountutil/mountutil.go`, `handleNamedVolumes` → `volStore.CreateWithoutLock`).
4. Итог: **два тома с одним именем**. Пустой «API-том» с compose-labels — в `default`; том с
   реальными данными — в ns проекта, без единого label. `docker volume ls` показывает оба
   (список идёт по всем namespace, `volumes.go:55-109`), `docker volume inspect` возвращает
   «не тот» (первый найденный).

Живое подтверждение в `guest-agent.log:487-492` (сессия 11.07): volume inspect
`pprb_uzp_efficiency_slave-data` падает в ns `default` («volume.json does not exist»), следом
`POST /volumes/create` — и том появляется именно там, а не в ns контейнера.

**Чем опасно.** Тихая дивергенция: prune/down -v чистят labelled-том из `default` (пустой),
данные живут без меток и не видны управлению. Состояние «работает» держится ровно до
пересоздания контейнера/тома.

**Обход, зашитый в проект.** Named volumes не используются вовсе: данные — в bind-маунты
(папка проекта на хосте через virtiofs-шару `/Users`) или вне VM.

### 4. `compose up` не подключает маунты (при этом `compose run` подключает)

**Статус: ПОДТВЕРЖДЁН** как следствие №3 + №5.

**Симптом.** После `compose up` у сервисов нет маунтов; `compose run` тем же сервисом —
маунт есть. `compose down -v` не сбрасывал базу.

**Диагностика.** Первый `up` срабатывает по сценарию №3: compose предварительно создаёт том
проекта через API → тот попадает в ns `default`; контейнер монтирует автосозданный том из ns
проекта. Раз «маунт подключился не туда», а inspect к тому же показывает `Mounts: null` (№5),
наблюдение «up не подключает» — честный вывод из того, что видно клиенту. К моменту
`compose run` том **уже автосоздан первым up'ом в ns проекта** — run монтирует именно его,
отсюда «run подключает». (Это наиболее вероятное объяснение, полностью согласующееся с кодом;
клиентская разница путей up/run в compose v5.3 в репо не проверяема.)
`down -v` же удаляет тома по label-фильтру `com.docker.compose.project` → находит и удаляет
пустой том из `default`, том с данными (без labels) не трогает → «база не сбросилась».

**Чем опасно.** Залипшее состояние между циклами up/down: тестовые данные переживают
«пересоздание с нуля», миграции молча пропускаются.

**Обход, зашитый в проект.** Compose убран полностью: прямые `docker run` c bind-маунтами
из make-скриптов.

### 5. `docker inspect` врёт — `Mounts: null` при работающих биндах

**Статус: ПОДТВЕРЖДЁН** (в HEAD).

**Симптом.** У контейнера с рабочим bind-маунтом inspect показывает `"Mounts": null`.

**Диагностика.** Структура ответа `dockerContainerInspect` (`guest-agent/containers.go:351-362`)
**не содержит поля Mounts вообще** — Go просто не сериализует то, чего нет. `HostConfig`
в inspect возвращает только AutoRemove/NetworkMode/PortBindings/RestartPolicy
(`containers.go:1610-1617`) — `Binds` тоже не возвращается. При этом nerdctl inspect маунты
знает (`inspectDetailsFor` парсит его ответ), но поля Mounts из него не читаются. Бонус:
`system/df` отдаёт `Mounts: []` для всех контейнеров и фейковый mountpoint томов
(`guest-agent/inspectextra.go:267,277`).

**Чем опасно.** Любой инструмент, который принимает решения по inspect (compose, свои
скрипты, оркестрация), видит «контейнер без маунтов»; аудит реальных биндов через API
невозможен. Это ещё и усилитель №3/№4: нельзя даже заметить подмену тома.

**Обход, зашитый в проект.** Не доверять inspect; конфигурация маунтов известна из своих
make-скриптов.

### 6. Нет DNS между контейнерами

**Статус: ЧАСТИЧНО ИСПРАВЛЕН** — для compose есть /etc/hosts-эмуляция (с багами), для
plain `docker run` DNS нет.

**Симптом.** Сервисы не находят друг друга по имени; база доступна только через
`192.168.64.1:5433` (шлюз vz-VM = macOS-хост, т.е. через опубликованный порт хоста).

**Диагностика.** Встроенного DNS-сервера Docker (127.0.0.11) нет. В v1.0.56 вошла эмуляция
(`guest-agent/networkalias.go`, коммит `2a5e6b9` от 15.08): алиасы сервиса из
NetworkingConfig запоминаются при create и при **старте** контейнера дописываются
`<ip> <алиасы>` в /etc/hosts всех контейнеров того же namespace. На 11.07 (сессия в
`guest-agent.log`) этого ещё не было — наблюдение «нет DNS» для той версии верно.
Остаточные проблемы в HEAD:
- **гонка ключей:** `pendingNetworkAliases(containerdID)` игнорирует свой аргумент и
  возвращает *любой* ждущий набор (`networkalias.go:33-42`), а `applyNetworkAliases` забирает
  из map первый попавшийся (`networkalias.go:73-84`) — при параллельном `compose up` алиас
  может получить **чужой IP**;
- **стейл-IP после recreate:** «идемпотентность» пропускает обновление, если имя алиаса уже
  есть в файле (`networkalias.go:104-108`) — у нового контейнера новый CNI-IP, но в hosts
  остаётся старый;
- plain `docker run --network X` (без compose-алиасов) разрешения имён не получает вовсе.

**Чем опасно.** Приложение ходит в БД через хост: контейнер → NAT → macOS → снова в VM →
контейнер. Лишний NAT-обвяз, лишняя точка отказа (см. №7) и скрытая зависимость от
проброшенного порта.

**Обход, зашитый в проект.** Обращение к базе через `192.168.64.1:<hostPort>` (публикация
порта на хосте), в крайнем случае `--add-host`.

### 7. Сеть рвёт сообщения ~60+ МБ — unexpected EOF на INSERT

**Статус: ВНЕ ANVIL** — в коде anvil лимитов нет; локализация — сетевой стек VM
(vzNAT/virtio-net) или CNI-мост.

**Симптом.** INSERT ~58 МБ проходит, ~90 МБ — обрыв (`unexpected EOF`), причём и через
`192.168.64.1:5433`, и по прямому IP контейнера.

**Диагностика.** Проверен весь дата-путь anvil — нигде нет ни лимитов, ни таймаутов на
передаче: хостовый Docker-прокси — байтовая помпа 64 КБ c writeAll без капов
(`Sources/vz-runner/DockerProxyServer.swift:155-213`); хостовый порт-форвардер — такой же
relay (`PortForwarder.swift:619-640`); guest port proxy — чистый `io.Copy` в обе стороны
(`guest-agent/portproxy.go:68-72`); exec-стрим — 4 КБ помпы без лимитов (`exec.go:274-296`).
Раз обрыв воспроизводится и **в обход** всех этих участков (прямой IP, контейнер→контейнер
через CNI-мост внутри VM), первопричина ниже userland: virtio-net/vzNAT стек Virtualization
.framework либо мост CNI. Порог 58/90 МБ выглядит как исчерпание буфера/кредитов передачи
на стыке NAT. Отладочные `netdbg.log`/`probe3.log` в репо содержат только заглушки проб —
сессия сетевого дебага не сохранилась.

**Чем опасно.** Молчаливая порча больших транзакций: загрузка «прошла наполовину» и
оборвалась на коммите; недетерминизм у порога.

**Обход, зашитый в проект.** Чанкинг: всё больше 32 МБ режется на куски до передачи.

### 8. Вывод контейнеров теряется — stderr всегда, stdout иногда

**Статус: ПОДТВЕРЖДЁН** — в attach есть три механизма потери вывода.

**Симптом.** Часть stdout команд не доходит до клиента; stderr ведёт себя стабильнее.
Важные команды дублируют вывод в файл на примонтированном томе.

**Диагностика (по коду attach, `guest-agent/dockerapi.go:136-270`).**
1. Реплей attach идёт через `nerdctl logs`, который пишет stdout контейнера в свой stdout,
   а **stderr контейнера — в свой stderr**; attach читает только stdout, а stderr
   **выбрасывает** (`dockerapi.go:190` — `io.Copy(io.Discard, stderr)`). Один из потоков
   теряется структурно.
2. Гонка реплея: логи опрашиваются 10×50 мс, follow (`logs -f`) включается только пока
   контейнер running (`dockerapi.go:209-219`). Быстро завершившийся процесс, чей вывод
   поздно сменился на диск (block-buffered stdout у pipelined-программ), теряет вывод
   навсегда — «stdout иногда».
3. `docker logs` склеивает оба потока в один stdout-стрим (`dockerapi.go:320` —
   `cmd.Stderr = cmd.Stdout`) — разделения потоков нет и там.

**Чем опасно.** Логи миграций/импортов теряются молчаливо: команда «прошла», а что она
напечатала — неизвестно. Для диагностики это минус ноль.

**Обход, зашитый в проект.** Важные команды пишут лог отдельным файлом на примонтированный
том; файл читается с хоста после завершения.

## Исторические / исправленные

### 9. compose считал завершённые run-контейнеры «orphan'ами»

**Статус: ИСПРАВЛЕН на стороне клиента** (обходом), в anvil не чинится — это семантика
compose: одноразовые `compose run`-контейнеры несут метки проекта, но не входят в текущий
файл сервисов → следующий `up` ругается на orphan'ов. Обход: `COMPOSE_IGNORE_ORPHANS=1`,
затем compose убран вовсе (см. №4).

### 10. BuildKit зависал на oauth-токене registry

**Статус: ИСПРАВЛЕН** — коммит `6d3a1c0` (15.08), пункт «buildkit OAuth pulls»: buildkitd
переведён на containerd-worker с `/etc/buildkit/buildkitd.toml`, `nerdctl build` закреплён
за сокетом через `BUILDKIT_HOST` (перестал напарываться на занятый сокет и плодить свои
buildkitd-инстансы), перед стартом вычищаются stale-процессы. Логи дебага — `bk-full.log`,
`bk-go-debug.log`, `bk-solve.log` (16.08): сессии pull+solve проходят, «cached auth handler
namespace … session finished: <nil>». Обход `DOCKER_BUILDKIT=0` больше не нужен (и не помогал
после №1, т.к. классический путь тоже шёл в buildkitd).

### 11. `compose run` panic и port collision при recreate

**Статус: ИСПРАВЛЕН** — тем же `6d3a1c0`:
- panic: inspect не возвращал HostConfig вообще → nil-deref в `container.RunStart` docker
  CLI; теперь inspect возвращает HostConfig (AutoRemove/NetworkMode/PortBindings/
  RestartPolicy) и Config Tty/OpenStdin/Env/Cmd/Entrypoint (`containers.go:1610-1624`);
- port collision: nerdctl резервировал host-порты **на create** унаследованным listener-fd,
  а compose при recreate создаёт замену до остановки старого контейнера → гарантированный
  конфликт. Порты больше не передаются nerdctl вовсе; маппинги пишутся в его network store
  (`containers.go:730-747`), публикация идёт через guest port proxy :39131 + хостовый
  PortForwarder, конфликт проверяется на старте как у Docker (`containers.go:1032-1051`,
  `portcheck.go`).
Закрыто регресс-тестами: `test_compose_recreate_over_live` и `test_compose_run_one_off`
(`scripts/integration_tests.py:483,515`). Уход после переустановки и клиента 29.7.2
подтверждается тест-матрицей (19/19).

## Что стоит починить в anvil (по следам аудита)

1. **Mounts в inspect** (`containers.go`) — читать из nerdctl inspect и возвращать честный
   `Mounts` + `HostConfig.Binds`; это закрывает №5 и делает видимой №3.
2. **Единый namespace для томов** (`volumes.go:172`): создавать том в ns проекта по label
   (или искать по всем ns при create контейнера) — это закрывает №3 и №4.
3. **`POST /containers/{id}/commit`** — минимальная реализация через nerdctl commit
