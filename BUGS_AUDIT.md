# Аудит багов — no-nerdctl ветка (август 2026)

Обновлённый аудит после переписывания гостевого агента на нативные API
containerd/buildkit (старый аудит удалён вместе с nerdctl-эрой). Базовый
прогон интеграции на момент начала: **43 passed / 7 failed**. После фиксов:
**49 passed / 1 failed** (см. «Известные ограничения»).

Все фиксы воспроизведены вручную и покрыты прогонами `make integration`
с холодной загрузки (`make service-debug-rebuild`).

## Починено в этом проходе

### 1. `docker cp` в запущенный контейнер: 137 / вечное зависание
- **Симптом.** `docker cp file ctr:/path` падал с `tar extract failed (137)`
  или зависал навсегда.
- **Диагноз.** Два слоя: (а) exec-процессы с stdin в containerd никогда не
  видят EOF на stdin-fifo (cio не закрывает fifo для one-shot писателей),
  поэтому `tar -xf -` внутри контейнера висит; (б) my-вариант с повторным
  монтированием снапшота rootfs пишет в ЧУЖОЙ overlayfs-upper — файл
  «скопирован», но контейнер его не видит.
- **Фикс.** Для запущенных контейнеров tar извлекается прямо в живой rootfs
  задачи `/run/containerd/io.containerd.runtime.v2.task/<ns>/<id>/rootfs`;
  для остановленных — прежний маунт снапшота. `runSimpleExecStdin`
  приведён к жизненному циклу `handleExecStart` (Start → Wait → IO().Wait →
  закрытие пайпов) с ограниченным таймаутом.

### 2. Гонка GC: «unpack ... content digest not found» (~25% compose-сборок)
- **Симптом.** `compose up --build` стабильно падал на распаковке свежего
  образа: скопированные блобы «исчезали».
- **Диагноз.** Копия образа между namespace'ами containerd создаёт запись
  (GC-корень дерева) ПОСЛЕ копирования блобов. Параллельный GC-проход
  (триггер — удаление любого образа, например `down --rmi` предыдущего
  проекта) удалял ещё не привязанные блобы. Форензика по namespace'ам
  показала: блоб записан «успешно», но отсутствует в целевом ns.
- **Фикс.** Копирование выполняется под containerd lease (созданным в
  целевом namespace — lease из default ns не защищает чужие записи!),
  родительские блобы получают метки `containerd.io/gc.ref.content.*`, после
  копии дерево верифицируется (один ретрай), `ensureImageInNamespace`
  при ошибке ждёт 500 мс и пробует ещё раз (финиширующий экспорт buildkitd).

### 3. `--restart`-монитор: политика гасла за секунды
- **Симптом.** «container was not restarted after failure» при живом
  мониторе.
- **Диагноз.** Бюджет `on-failure:N` тикал на каждый цикл ОПРОСА (~1/с), а
  не на попытки рестарта: неудачный старт (см. п.4) сжигал бюджет за 3
  секунды. Плюс рестарты бились о «veth already exists» — CNI-detach
  exit-watcher'а асинхронен.
- **Фикс.** Бюджет считается по фактическим попыткам; attach CNI
  самолечится: при любой ошибке attach выполняется DEL и повтор.

### 4. `--memory`: лимит не виден в контейнере
- **Диагноз.** В спеке не было приватного cgroup-namespace и маунта
  cgroup2 — runc маскировал /sys/fs/cgroup пустым tmpfs.
- **Фикс.** `Linux.Namespaces += CgroupNamespace` + mount
  `/sys/fs/cgroup type cgroup` — runc подменяет его на собственное subtree
  контейнера; `cat /sys/fs/cgroup/memory.max` показывает лимит.

### 5. `--network host`: контейнер видел только lo
- **Диагноз.** Default-спека containerd всегда добавляет свежий
  NetworkNamespace — «host» режим просто игнорировался.
- **Фикс.** При host-режиме NetworkNamespace удаляется из спеки — задача
  разделяет netns гостя (eth0 виден).

### 6. `docker save` нескольких образов / multi-arch
- **Симптом.** `save` нескольких тегов давал 0–1536 байт либо
  «content digest not found».
- **Фикс.** Сериализация save (общий scratch-namespace), строгая проверка
  видимости каждого манифеста в scratch после копирования (неполные
  манифесты выбрасываются из пересобранного индекса), пуллы с ретраями.

### 7. `docker system prune` зависал на 300+ секунд
- **Диагноз.** Клиент buildkit не закрывает канал usage-записей — дренаж
  ждал вечно.
- **Фикс.** Дренаж ограничен 2 секундами.

### 8. DNS-флейки гостя (buildkitd «lookup auth.docker.io: i/o timeout»)
- **Диагноз.** Go-резолвер игнорирует `single-request` и шлёт A/AAAA
  параллельно; форвардер VZ NAT дропает один из них, а `attempts:3`
  тратил все попытки на битый сервер.
- **Фикс.** resolv.conf гостя: публичные резолверы первыми, DHCP-DNS
  последним, `timeout:1 attempts:2`. Пуллы в агенте ретраятся 3 раза.
  Примечание: buildkitd резолвит FROM через registry всегда; локальный
  fallback (ResolveMode default) срабатывает при недоступности хаба.

### 9. Прочее
- Логи buildkitd пишутся на virtiofs-шару (`buildkitd.log`) — доступно с
  хоста для диагностики.
- `logs -f` и attach используют общий стоппер по состоянию задачи;
  follow перечитывает лог по пути (логгер может заменить файл целиком) и
  завершается по «тишине» (2 c без новых байт), а не по первому опросу.
- Дебаунс стоп-условия в фазе открытия лог-файла (быстрый контейнер не
  должен обрезать собственный вывод).
- Удаление сети по ID (compose down) ищет conflist по имени.

## Известные ограничения (не баги агента)

1. **Финальный вывод без `\n` теряется** (`printf tail`, `... | head -c N`).
   Байты последнего write(2) умирающего процесса не доезжают до
   logging-бинаря: контейнердовский binary-v2 IO закрывает пайп задачи
   раньше, чем читатель успевает их забрать. Полные строки стримятся
   вовремя; любой вывод ПОСЛЕ хвоста вымывает всё (проверено: `dd 15 zero`
   + `echo` доставляет и нули, и метку). Это поведение
   containerd-shim-runc-v2, не агента; единственный падающий тест сьюта
  (`--link` probe с `wget | head -c 15`) упирается именно в это.
   Таймерный флаш partial-строк в логгере оставлен (покрывает случай, когда
   байты всё же дошли), но проблему на уровне шима он не решает.
2. **`FROM` в Dockerfile резолвится через registry.** При полностью
   лежащем Docker Hub сборка с НОВЫМ базовым образом невозможна (локальный
   fallback срабатывает только для уже скачанных тегов).
3. **Сьют сам удаляет `alpine:latest`** (тест self-heal), и последующие
   тесты зависят от повторного пулла: при сетевых окнах к хабу возможны
   каскадные падения, не связанные с кодом агента.
